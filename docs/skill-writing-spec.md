# Skill 编写规范(influx-ai)

本文档约定本仓库内所有 `SKILL.md` 的写法和验收方式。新写或重写任何 skill 前先读本文。

依据(2026-11-12 核对):

- [Agent Skills 规范](https://agentskills.io/specification)
- [Skill 创作最佳实践](https://agentskills.io/skill-creation/best-practices)
- [Anthropic: Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)

规则来源标记,每条规则只用一个标记:

- **【要求】** 官方规范明确要求,违反会导致 skill 无效或校验失败。
- **【建议】** 官方建议,有充分理由才偏离。
- **【约定】** 本仓库自定,官方没有要求。**未带标记的条目按【约定】处理。**

适用范围:**新写和重写的 skill 必须达标;存量 skill 在被修改时顺带达标,不要求一次性整改。** 存量中不符合本规范的内容(如含"来源项目""未核对"之类的开发者备注、`node ../../scripts/...` 写法)不视为缺陷,改到哪里整理到哪里。

---

## 1. 核心原则

1. SKILL.md 是操作手册,不是设计文档。读者是 Agent,目标是让它按文档把任务做对。
2. 只写 Agent 不知道的。项目专有的调用方式、字段含义、易错点要写;通用常识(HTTP、JSON、UUID)不写。【建议】
3. 给默认值,不给菜单。有多种做法时选一个默认,备选一句带过。【建议】
4. 写方法,不写特例答案。写"怎么做一类事"的步骤。【建议】
5. 每条规则问一句:不写这句,Agent 会做错吗?答案是不会就删;拿不准就跑一遍测试(见 §9.3)。【建议】

## 2. 包结构与引用

### 2.1 包的定位

本仓库发布的是**一个包**:一个根 skill(`influx-ai/SKILL.md`)加若干子 skill。子 skill 是根 skill 路由到的"章节",各自有 `SKILL.md` 和 frontmatter,但**共享**包根的 `scripts/` 与 `references/`。

```
influx-ai/
├── SKILL.md                    # 根 skill,路由到子 skill
├── scripts/                    # 全包共享脚本
├── references/                 # 全包共享参考资料
├── discovery/<skill>/SKILL.md
├── outreach/<skill>/SKILL.md
└── tools/<skill>/SKILL.md
```

官方规范未描述嵌套 skill,客户端能否单独发现和激活子 skill 未经验证。因此本规范不要求子 skill 可脱离包独立安装。

### 2.2 路径与引用规则

- **链接路径相对于当前文件所在目录。** 子 skill 可以用 `../../scripts/`、`../../references/` 指向包根的共享资源。(官方原文是"相对于 skill 根目录",此处因包结构而调整。)
- **命令的执行目录在"前置条件"中写明,全包一致。** 新写或重写的 skill 统一为:从包根目录(`influx-ai/`)执行,写作 `node scripts/xxx.mjs`。存量 skill 当前写作 `node ../../scripts/...`,迁移前保持原样。
- **"引用保持一层"只数 SKILL.md 到 reference 的层级。** SKILL.md 直接链接每个 reference,reference 不再链接其他 reference。【建议】skill 与 skill 之间的路由链接(根到子、子到子)不受此限。
- **每个 reference 链接都写明何时读。** 例如"收到非 2xx 时读 `references/error-codes.md`"。不写"详见 references"。【建议】
- 超过 100 行的 reference 文件顶部加目录。【建议】
- 路径一律用正斜杠。【建议】
- 链接目标必须存在,由 `tests/check-skills.cjs` 检查。
- 推荐目录名 `scripts/`、`references/`、`assets/`。【建议】

## 3. Frontmatter

```yaml
---
name: creator-email-lookup
description: 第三人称,说明做什么 + 何时使用,含触发关键词。
---
```

`name`:

- 1 到 64 字符;仅小写字母、数字、连字符;不以连字符开头或结尾;不含连续连字符 `--`;与所在目录名一致。【要求】
- 不含 XML 标签,不含保留词 `anthropic`、`claude`。【要求】(Anthropic 平台)
- 用名词短语或动名词表达能力,避免 `helper`、`utils` 这类泛称。【建议】

`description`:

- 非空,不超过 1024 字符。【要求】
- 不含 XML 标签。【要求】(Anthropic 平台)
- 同时写**做什么**和**何时用**,包含用户可能说的关键词。【建议】
- 使用**第三人称**("查找指定达人账号的邮箱……"),不用"我可以""你可以"。这是 Anthropic 平台约定。【约定】
- 与其他 skill 的分流用一句话写在触发条件里。

可选字段:`license`、`compatibility`(运行环境,如 `Node.js 20.6+`;多数 skill 不需要)、`metadata`(键名保持唯一)、`allowed-tools`(实验性,默认不用)。

## 4. 正文结构

官方对正文**无格式限制**。以下为推荐顺序,无内容的章节省略,不写占位。

| 序号 | 章节 | 内容 |
| --- | --- | --- |
| 1 | 标题 + 一句话用途 | 解决什么问题 |
| 2 | 前置条件 | 运行环境、环境变量(只写变量名)、执行目录 |
| 3 | 操作总览 | 表格:用户意图 → 脚本 → 副作用 |
| 4 | 标准流程 | 编号步骤,每步一条命令,标出需要用户确认的节点 |
| 5 | 各操作详情 | 见 §5 |
| 6 | 结果解释与展示 | 状态含义、展示模板 |
| 7 | Gotchas | 易错点 |
| 8 | 延伸阅读 | 带读取条件的 reference 链接 |

**Gotchas 的写法:** 写 Agent 不知道就会做错的具体事实,例如"HTTP 202 只表示受理,不代表找到邮箱"。不写"妥善处理错误"这类泛泛建议。Gotchas 必须放在 SKILL.md 正文:Agent 在遇到情形之前,未必意识到该去读另一个文件。【建议】

**正文长度:** 不超过 500 行。【建议】官方同时建议约 5000 token,但中文难以稳定估算,本仓库只检查行数。

## 5. 操作详情模板

每个脚本/操作写一节。**基础块**所有操作都有;**扩展块**按操作类型出现。

````markdown
### 操作名(`scripts/xxx.mjs`)

用途:一句话。类型:只读 / 有副作用 / 有费用 / 异步。

**输入**

| 字段 | 必填 | 含义 | 默认/约束 |
| --- | --- | --- | --- |

**输出**

| 字段 | 含义 |
| --- | --- |

**示例**

```bash
node scripts/xxx.mjs '<JSON 参数>'
```

```json
{ "success": true, "data": {} }
```

**注意**:该操作特有的坑,1 到 3 条。
````

扩展块:

| 操作类型 | 追加内容 |
| --- | --- |
| 有副作用或有费用 | **确认点**:执行前向用户确认什么(对象范围、费用来源)。**重试规则**:能否重试,幂等键如何保留,超时后怎么办。 |
| 异步 | **状态流转**:有哪些状态,哪些是终态。**轮询规则**:间隔、最大次数及依据,超出预算后怎么办。 |
| 批量或不可逆 | 按 plan → validate → execute 写:先产出计划,校验通过再执行。【建议】 |

规则:

- **示例命令按脚本实际入参形式写。** 目前 discovery 脚本只接受位置参数 JSON(`node scripts/x.mjs '{...}'`);email-lookup 与 outreach 脚本额外支持 `--input-file <本地JSON路径>`。含敏感内容或较长的请求,在脚本支持时优先用文件形式。
- 输入表列必填和常用字段;完整约束(长度上限、枚举全集、别名)放 reference。
- 输出表列**出现在后续步骤条件或展示模板里的字段**;其余放 reference。
- 示例用虚构数据,字段结构与真实响应一致。不得使用真实账号、邮箱、ID。
- 请求示例替换占位值后可直接运行。
- 轮询间隔、重试次数等数值必须有依据(服务端建议、耗时统计),不写无来源的常数。

## 6. 内容取舍

**必须写进 SKILL.md:**

- 标准流程及每步命令
- 输入输出字段含义
- 需要用户确认的节点
- 结果状态的正确解读
- Gotchas

**放进 references:**

- 完整字段约束表
- 枚举全集、国家/语言代码等查表数据
- 错误码与逐项处理
- 极少触发的边缘场景

**不要写:**

- **开发进度和验收状态**,如"尚未验收""一期没有 X"。这类内容放 CHANGELOG 或 README。脚本表中的运行能力标注(如"可用""异步")允许保留。
- **后端契约来源、manifest 路径**等开发者信息。
- **会过期的信息**:具体日期、"2026 年前"之类的条件。确需保留旧做法时,放在单独的"旧做法"小节。【建议】
- **通识解释。**
- **大段否定清单。** 只保留 Agent 会误做的那几条,并写明原因。

## 7. 控制力度

按任务的脆弱程度选择,同一 skill 内可混用:【建议】

- **高自由**:多种做法都可行(如何向用户组织结果)。说明目的,让 Agent 判断。
- **中自由**:有推荐模式,参数可调(如带默认值的脚本调用)。给出默认命令,说明哪些参数可以调整。
- **低自由**:有副作用、有费用或必须按序执行。给出精确命令和顺序,注明不可改动的部分。

## 8. 写作风格

- 同一概念全文只用一个词(如统一用"批次",不混用"任务")。【建议】
- 用短句、列表、表格;一个段落只讲一件事。
- 展示格式用模板代码块。【建议】
- 多步流程用编号清单。【建议】
- 写具体动作,不写"妥善处理""按需处理"。
- 明确执行意图:"运行 `scripts/x.mjs`"与"阅读 `references/x.md`"分开写。【建议】
- 文件名有描述性(`email-lookup-fields.md`,不用 `doc2.md`)。【建议】
- 依赖(Node 版本、环境变量)在前置条件中声明,不假设已安装。【建议】

## 9. 验收标准

分三层。每条都必须能判断通过与否。

### 9.1 机器检查(脚本)

运行 `node tests/check-skills.cjs`(全部 skill)或 `node tests/check-skills.cjs influx-ai/tools/<skill>`(只查指定 skill)。有失败项时退出码为 1。

| 检查项 | 来源 |
| --- | --- |
| `name` 格式、不含保留词和 XML 标签、与目录名一致 | §3 |
| `description` 非空、≤ 1024 字符、不含 XML 标签 | §3 |
| SKILL.md ≤ 500 行 | §4 |
| SKILL.md 中的链接目标存在、路径无反斜杠(代码块内不算链接) | §2 |
| 被链接的超过 100 行的 reference 有目录(判定:前 20 行内有标题含"目录"或"Contents") | §2 |
| 命令中的脚本路径指向存在的文件。同时兼容 `node scripts/x.mjs`(相对包根)和存量的 `node ../../scripts/x.mjs`(相对 SKILL.md 所在目录) | §5 |
| `scripts/` 下 `.mjs` 语法正确;`skill.json`、manifest、根 SKILL.md 版本一致(仅全量检查) | 发布 |

已知盲区:

- 只检查 `influx-ai/` 下的 SKILL.md 和被它们直接链接的 reference,不检查 `docs/`。
- 只识别 `node ...scripts/x.mjs` 形式的命令。
- 不检查第三人称、术语一致、示例是否为虚构数据等,这些见 §9.2。

**manifest:** 改动包内任何文件后,在 `influx-ai/` 下运行 `node scripts/generate_manifest.mjs` 刷新 `skill-manifest.json`(哈希按原始字节计算,与 `.gitattributes` 的 `-text` 约定一致);`node scripts/generate_manifest.mjs --check` 只检查、不写入,清单过期时退出码为 1。`local-requests/` 等本地资料不会列入清单。

可同步使用官方 `skills-ref validate <skill目录>` 校验 frontmatter。

存量 skill 目前有失败项(description 超 1024 字符、creator-search 超 500 行、部分 reference 缺目录)。按"适用范围"一段,存量改到哪里整理到哪里;新写和重写的 skill 必须全部通过。

### 9.2 人工检查

结构与内容:

- [ ] 标准流程的每一步,命令、必填字段、确认点都在 SKILL.md 内。
- [ ] 每个操作都有输入表、输出表、命令、示例。
- [ ] 有副作用或费用的操作写了确认点和重试规则;异步操作写了状态流转和轮询规则。
- [ ] Gotchas 放在 SKILL.md 正文,每条是具体事实。
- [ ] 无开发进度、契约来源、会过期的信息。
- [ ] 术语一致。

示例与数据:

- [ ] 示例全为虚构数据,字段结构与真实响应一致。
- [ ] 请求示例替换占位值后可运行。
- [ ] 轮询间隔、重试次数等数值有依据。
- [ ] 示例命令的入参形式与脚本实际一致。

引用与表述:

- [ ] 每个 reference 链接都写明读取条件;引用不超过一层。
- [ ] 执行意图("运行"与"阅读")分开写,文件名有描述性,依赖在前置条件中声明。
- [ ] description 为第三人称,含做什么和何时用。
- [ ] 脚本相关:出错时非零退出码,错误信息含原因;敏感信息不出现在命令参数、示例和日志里(见 §11)。

### 9.3 实测

1. **先定场景和通过条件。** 至少 3 个真实场景,每个写明可判定的通过条件,例如"未经 preview 与用户确认就 create,视为失败"。
2. **跑基线。** 同一批场景先不带 skill 跑一遍,记录失败点。
3. **带 skill 再跑。** 对比基线,确认 skill 带来了提升。基线本来就做得很好的部分,说明 skill 没有增益,应精简。
4. **读执行轨迹**,不只看最终结果。Agent 反复自行摸索的步骤、做了多余操作的地方,都说明文档需要改。
5. **回写。** 做错的地方补进 Gotchas,没用到的内容删除,再跑一轮。

## 10. 迭代顺序

先评估,再动笔:【建议】

1. 按 §9.3 第 1、2 步建立场景和基线,记录 Agent 失败或绕路的地方。
2. 根据失败点和现有材料(脚本、契约、测试)写最小的第一版,只覆盖这些缺口。
3. 按 §9.3 第 3 到 5 步复测。
4. Agent 反复重写的相同逻辑,沉淀为脚本放入 `scripts/`。

## 11. 脚本相关

- 出错时返回非零退出码,错误信息写明原因和下一步,不把问题丢给 Agent 去猜。
- 在 SKILL.md 说明依赖版本和所需环境变量(只写变量名)。
- 敏感信息(密钥、令牌)通过环境变量或受保护配置注入,不出现在命令参数、示例和日志里。
- 新增脚本建议支持 `--input-file <本地JSON路径>`,避免较长或敏感的请求进入命令历史。存量脚本不强制改造。
